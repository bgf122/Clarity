# Clarity: Anarchy Online client UI mod

Clarity is a 32-bit mod DLL that improves the AO client UI. It loads as a `dinput.dll` proxy.

Machine-specific notes (client paths, test setup) go in `CLAUDE.local.md`, which is not in git.

## Layout
- `src/`: mod source.
  - `proxy/` is the `dinput.dll` proxy.
  - `core/` holds the log, INI config, signature scan, MinHook wrapper and renderer access.
  - `features/<name>/` holds one folder per feature.
- `src/core/signatures.h`: byte signatures for non-exported client functions. `tools/verify_sigs.py <client dir>` checks that each one matches exactly once.
- `third_party/minhook`: vendored MinHook 1.3.4.
- Work on a **test copy** of the client, never on your real install. Re-confirm RE findings against the test client's bytes, e.g. with the Ghidra MCP servers in `.mcp.json` (copy `.mcp.json.example` and fill in your paths).

## Build and deploy
Use the CMake bundled with VS 2022, and target 32-bit (Win32):
```
"C:\Program Files\Microsoft Visual Studio\2022\Community\Common7\IDE\CommonExtensions\Microsoft\CMake\CMake\bin\cmake.exe" -S . -B build -G "Visual Studio 17 2022" -A Win32 -DDEPLOY_DIR=<test client dir>
"...\cmake.exe" --build build --config Release
python tools/verify_sigs.py <test client dir>
```
- The post-build step copies `dinput.dll` to `DEPLOY_DIR` (empty = no copy). The game must be closed, because the DLL is locked while it runs.
- The version is `project(Clarity VERSION ...)` in `CMakeLists.txt`. It goes into the DLL's VERSIONINFO (ProductName "Clarity"), which the AoForge installer reads.
- Releases: pushing a `v*` tag runs `.github/workflows/release.yml`, which builds and attaches `Clarity-<version>.zip`.
- Patch notes: add a `## <version>` section to `CHANGELOG.md` before tagging. Write it for players, not as RE notes. The workflow makes that section the release's notes, which AoForge shows per version, and a tag without a section fails.

## Per-install AO data
AO keeps prefs, `DXDiagOutput.txt` and the GUI in `%LOCALAPPDATA%\Funcom\Anarchy Online\<hash>\client\`.
- **How the game computes `<hash>`** (`BinaryIO!AnarchyPath_t::GetUserDataPath`): it takes the parent of the client dir, from the ANSI cwd with `/` separators and no trailing slash, e.g. `C:/Project Rubi-Ka`. It hashes that with boost `hash_combine` over *signed* chars: `h ^= c + 0x9e3779b9 + (h<<6) + (h>>2)`. The result is printed with `%x`.
- The PRK launcher hashes the path differently. For ASCII paths the two agree, but with non-ASCII paths they don't, so keep test clients on an ASCII path.
- A fresh client copy has its own hash folder. Seed it from your real install's folder, or the game runs on defaults: a tiny window and the "display driver/device combination" warning.

## Testing
- Launch the game from the test copy and log in.
- `Clarity.log` in the client folder should contain `[hook] ... installed` and `[fct] ready`.
- Also check `AOReloaded.log` and `randy-vk.log` there for new errors.
- `Clarity.ini` is reloaded live (polled every 0.5 s).
- With `[FloatingText] Debug=1`, every floating text is logged with its colour index and projection values.

## How the mod loads, and coexisting with other mods
- **Loading.** The game exe is `AnarchyOnline.exe`. `Anarchy.exe` is the old patcher and is not used. `DisplaySystem.dll` imports `dinput.dll`, so our proxy loads in the game process only, not in CEF helpers. `DllMain` only starts a thread. Hooks go in after Gamecode/DisplaySystem/randy31 are loaded.
- **Other mods.** These may already be in the process. Do not hook their targets:
  - `version.dll` = AOReloaded (`AOReloaded.ini`): movement, input, inventory and skill-window hooks, `CreateFileW/A` import patches, and it patches the exe on disk.
  - `randy31.dll` = ao-vk (randy-vk Vulkan renderer): forwards data exports to `randy31_orig.dll`, and hooks `View::_CallRender` and `WindowController_c::Render`.
  - `aonewbie-hook.dll` (external, Detours): `N3Msg_*`, `DataBlockToMessage`, `TextView_c::SetText`, `RunEngine`.
- **Finding targets.** Prefer exports, resolved by mangled name. Only use signatures for non-exported functions. On a signature mismatch the feature disables itself and logs. Never patch blindly.
- **Address math.** Client DLLs have image base 0x10000000 but are relocatable. Always compute module base + RVA.

## Floating combat text (src/features/fct)
- **Created by:** Gamecode `CreateFloatingText(dynel, text, colorIdx)` (stdcall) → effect 0x2F5A `_GfxControlFont_t`.
- **Drawn by:** `DisplaySystem!GfxVisualDiaBill`, as a camera-facing billboard built from `DiaBill_n::Sprite_t` (0x20 bytes each) and the 128×64 `spritefont.png` atlas.
- **Our hooks:**
  - `SetText`: swaps in our sprite array (shadow + 8 outline + glyph layers) with `GfxVisualDiaBill::Init`.
  - `Process`: rewrites the array each frame for constant pixel size, using `RViewPort_t::m_CurrentViewMatrix`/`m_CurrentProjectionMatrix` and the window height.
- **Next milestone:** replace the 12 px aliased atlas with a high-res antialiased one. This needs RE of how `MMGetMaterial(40)` loads `spritefont.png`.

## Features
- `src/features/fct`: floating combat text. It uses exact crits and glancing hits (AttackInfo hit type at [ebp+0x20] in the combat function), drain heals (CharacterAction 0xD0), and hides others' damage by chat group (read from the caller frame).
  - The combat-message function (SIG_COMBAT_MESSAGE, `__thiscall(event, target, amount, attacker, special, dmgType, hitType, x)`, ret 0x20) makes floating text only for a non-zero amount; several cases leave through the exit that zeroes it, so Clarity adds text after the original: 0x3B miss, 0x41 you healed, 0x43 you gave nano, 0x44 got nano from someone. Events 0x42-0x44 are sent from the CharacterAction handler.
  - CharacterAction 0x8C = "You increased your nanopool with %d points" (amount in p28[1]). The handler (this = the character whose action it is) also gets other characters' actions and its 0x8C case doesn't check, so Clarity shows 0x8C, and 0x43 / 0x44 (sent from there with that character as the attacker), only when it is the client character (+0x140).
  - Names shown over the performer: special attacks colour 13, perks/actions 3, taunts 2 (hidden over other players unless OthersSpecials).
  - With `Debug=1`, every combat event and CharacterAction is logged.
- `src/features/nameplates`: two styles ([Nameplates] Style): Classic (0, default; RenderText) and Modern (1, RenderModern: 0.1.14's plates - level beside the name, flat bar with the percentage on every plate, corner brackets on targets, red brackets for attackers, BackgroundOpacity panel, [Nameplates] Font/FontWeight; its options ClickToTarget, ShowLevel, ShowOrg, ShowHealth, BarColor (level / health), BarBrightness apply only to it). Classic: the game's nametag Indicators get our own VisualMaterial_t texture: the name (title first) in a frame like the bars' (silver rim with cut corners, gap, inner ring, dark panel, teal lower corners), Bahnschrift, and the org line under the frame. Only the selected / fight target plates have a health bar. Click-to-target, title and org are always on (no options). Sizing is per frame from the RSprite vertices. Per-type visibility uses VisualSprite_t::SetInvisible after the game's update. The Indicator vtable slot 0 is hooked to free our texture. The selected target's and fight target's indicators (+0x31 / +0x30) get the same plate with its inner ring white / orange (gold and a single plate when it's the same character), bigger than other plates (TargetScale, default 1.1). Turning nameplates off restores the game's material and quad on every Indicator.
  - Plates are drawn without depth test and hidden behind walls/terrain by `N3!n3Playfield_t::LineOfSight(from, to, zone -1, false)` from the camera (CameraWorldPos from the view matrix), tested every 100 ms per plate. The selected and fight target plates skip the test and show through everything, but are hidden beyond 80 m from the player (kTargetRange, 3D distance). In front of the camera they are also kept inside the window: the quad is shifted in the camera plane (vertex offsets, `rightSign` from the texture u) so the plate stops at the edge.
  - Names (NameRuns) as the game's tag builder (GUI 0x10024E14) shows them: the title first, on the name line ("Title ** Name **"; the second line is the org only); colour codes inside a name (byte 0x10 + colour code, resolved by FontSystem_t like NameRgb) switch the colour; players get "** name **" when stat 224 has bits 0x4000001 (PvP flag), "= name =" for stat 673 bit 9.
  - Your own character has a plate when you target yourself (classed as a player), or always (whatever ShowPlayers says) with Modern's ShowSelf: GUI.dll's import slot for N3Msg_GetDynelsInVicinity is chained, and the call from TargetingModule_t::HandleNametags (2 s scan, return address in 0x10025D96..0x10025FA4) gets includeSelf = true (WantSelf: Enable, Style Modern, ShowSelf; a change forces a rescan). Hidden in first person.
  - Characters attacking us (core/threat: damage on us with a known attacker, misses on us, the game's "Attacking You!") get a blinking red band right on the frame's rim (atkFill / atkOutline masks, painted by Repaint). All plates reserve room for it.
  - Texture 1024x256 (long names at full size; ao-vk's label test needs width >= 2x height).
- `src/features/hideui`: a key ([Interface] HideUiKey, default Ctrl+Shift+U, seen in the game window's procedure, core/wndproc) hides the interface and keeps the plates. The interface is one entry of DisplaySystem's SpriteRenderSystem_t list (WindowController_c's RenderSpriteBase_t part; the list is a std::list whose entries get vtable slot 1, Render(viewport, alpha), each frame from 0x1007BDBA). Hiding swaps that entry for a stand-in whose Render does nothing; nothing is hooked, and ao-vk shows its interface layer only from inside that call. `SpriteRenderSystem_t::AlphaFade` only fades the mouse pointer, not the windows.
- `src/features/bars`: health/nano, fight-target and nano-target bars in place of the game's ([Bars]). Three plain GUI windows (GUI.dll exports, nothing hooked): `Window` (constructor registers it with WindowController_c) -> `View` -> `ViewSurface_c` made from a `SpriteInfo_t` (DisplaySystem) Clarity paints, as TextRenderer_c (0x1016095B) does.
  - Sizing: a plain View has no preferred size and the window collapses to nothing; `Window::SetSizeLimits(size, size)` + `ResizeTo` pins it.
  - Sprite format: SpriteInfo_t Format_e 2 is the GUI's A1R5G5B5 (1-bit alpha). The bars preset D3DX A8R8G8B8 (2) at +0x38 and pass Format_e 3, which keeps it; falls back to the GUI's format if refused.
  - Uploads: `ViewSurface_c::UpdateTexture(sprite, Rect, Point)` sends only the tiles (16x16 ViewArea_c) under the content. Repainting the whole sprite many times a second cost ~10 fps; the fight target's pulsing outline is a second surface faded with `ViewSurface_c::SetAlpha`, never repainted. A health change (fill, amounts) repaints the canvas but sends only the bars' rectangle (Present's `bars` state and barsArea, Upload's `part`); the whole panel only when its layout or name changes.
  - Tried and dropped: fills as small one-colour sprites stretched with `SetDstFrame` (no upload on a health change). In game they looked blurry and faded (the GUI filters stretched surfaces).
  - Colours and shading of your health / nano bars: the Stats window's fill images (StatView_c ctor GUI 0x1007FF6E: PowerbarView_c(rect, background 0xDB, fill, 0, 0, horizontal); health 0xDD, nano 0xDA (XP 0xDE, alien XP 0xDC); GuiResourceManager_t::GetGuiTexture), averaged along the length: the bar's shading top to bottom (dark, bright middle, dark; Colours::shading), used as the fill's profile in place of Gloss. Target bars keep Gloss in the consider colours. (The game's own CharacterBar_c images 0x0D / 0x11 are upright, 35x200; no longer used.) Target bars use the game's consider colours (nameplates::ConsiderBarRgb); every name is in one colour (kLabelRgb).
  - Targets: fight = N3Msg_GetAttackingID, nano = InputConfig_t::GetCurrentTarget (n3::FightTarget / SelectedTarget), the nano target's target = N3Msg_GetTargetTarget(id) (hidden return; as CCTargetControl_c, GUI 0x10073B9E; n3::TargetOf). Stats: health 27 / max 1, nano 214 / max 221.
  - The game's bars are CharBarWindow_c windows (GUI 0x1006D7C7) in WindowController_c's window list (std::list at +0x88), found by RTTI class name and config name at +0x74 ("CCHealthBarConfig", "CCNanoBarConfig", "CCFriendlyHealthBarConfig", "CCHostileHealthBarConfig"); hidden while the bars are on, shown again via their CriteriaMonitor_c (+0x90) when off.
  - Dragging and the 33 ms update timer run in the game window's procedure (core/wndproc, shared with hideui and click-to-target); positions go to [Bars] in Clarity.ini.
  - Look: every panel is a painted frame (PaintFrameInto, once per size in g_frames): a 1 px dark outline with cut corners, gunmetal ring with steps, dark inner panel (10 px in to the bars' bezels), teal glow lines (Canvas::Chamfer / ChamferStroke / Polygon / Line). Bars sit in silver bezels with a glossy fill. The name is above the frame, outside it, in spaced capitals (no level), in Bahnschrift (Windows' DIN, as the reference image), always in full: a panel wider than its frame has the frame frameX in (NameOverFrame), and positions ([Bars] SelfX etc., homeX) are the frame's, so a long name doesn't move it. Your bars show the amount ("8,412 / 12,950"), no percentage; target panels have the health bar only, no numbers (a target with no health, an object or corpse: a slim empty frame, 2 x FrameCut + 2 high); the nano target's target panel is the name only (PresentName). The fight target's pulsing ring is the inner ring in orange (overlay surface).
  - Target health sections: the game's TargetHealthBar_c (GUI 0x10073598; vtable 0x101B5CAC; skin images TARGET_HB_BACKGROUND / _SLIDER 16x11, _LEFT / _RIGHT caps) tiles a 16 px image along its length, never stretching it (0x10072EAD). Its SetTarget (0x1007313A) sets the length from the target's max health (stat 1): floor(min + (max - min) * 0.01 * sqrt(2 * sqrt(maxHealth))), clamped to [min, max]; min = 64 (ctor, 0x101B5EBC), max = (screen width - 192) * 0.5 - 50 GUI units (0x100746EC). Clarity's bars keep their length and draw the game's number of sections, length / 16 (GameSections), narrower when there are many.
  - Your stats, as the game's Stats window (StatView_c, Ctrl+9) shows them: the level (stat 54) in teal left of your name, over the frame (as Modern plates); two lines under your nano bar, "Attack rating" (stat 22; GUI 0x1007FA7A) and "Melee/ma AC" (91), label left, number right (on one line they don't fit at Size 0.8), in the Stats window's colours: labels white, numbers #BBBBFF. Stat labels are in the game's own case, not capitals. After 400 ms of hovering over the "Melee/ma AC" line of your panel (cursor on that line, `GetMouseWindow` is your panel or none, game window in front; g_acRow) all eight ACs (melee too, for a whole list) show in a small frame under it, or above it if there's no room (g_selfStats; not dragged or clicked), it hides as soon as the mouse leaves. Window order: the Window constructor turns flags 0x200 / 0x100 into root-view flags 8 / 0x10, which `View::_LinkChild` keeps behind / in front of all other windows. The panels use the game bars' 0xE3C (has 0x200: behind everything, so `MoveToFront` alone left the popup under the chat window); the popup is made with 0x200 cleared and 0x100 set (kTopWindowFlags), plus `Window::MoveToFront` each time it opens. The ACs and their order are from 0x1007FAD8: Melee/ma 91, Imp/Proj 90, Energy 92, Disease 96, Chemical 93, Radiation 94, Cold 95, Fire 97. Labels are from text.mdb.
  - Unlocked, a left press drags a panel. Locked ([Bars] Locked=1), a left press on any panel selects whom it shows with `TargetingModule_t::SetTarget(id, false)`, as nameplate click-to-target does (on the press, the button-up swallowed); the self panel selects you.
- `src/features/effects`: scenery effects left out ([Effects] HideShipSmoke, on the options' Misc page; Hide = more effect ids; Debug=1 logs each id once). The ship smoke: the alien ship over the ICC Shuttleport (playfield 4582) - `ai_alien_lander.abiff` plus five `ai_effect_ship_smoke.abiff` markers, placed in the zone (`rdb_1000003`) - carries effect 12530, a `_GfxControlGlobalSmoke_t` (64 large bright alpha-blended sprites each): the glowing columns under the ship, heavy on the GPU. Switched live: a switchable effect is still created, Clarity keeps a reference to its connector (randy31 `RResource_t::AddRefRResource`), deletes the effect while hidden and creates it again on the same connector when shown; the hooked DeleteEffect ends ours with the game's handle, and a playfield change (`n3Playfield_t::GetPlayfield`) drops them. Effect definitions are `Setupf/gfxtweak.bin` (records: id, class, dword count, payload; class 2007 = `_GfxControlMeta_t` (children), 3004 = `_GfxControlSequencer_t`, 3006 = `_GfxControlSkyFlash_t`, 3017 = `_GfxControlGlobalSmoke_t`, 3022 = `GfxControlBeam_t`; class -> constructor in `_EffectHandler_t::CreateGfxControl(int, RConnector&)`). Meshes start effects through sub-meshes named `eff_universal_<id>` (DisplaySystem 0x1005F1D4 queues them for FXS-spawned meshes; statics placed in a zone go through `GfxStartlist_t`); both go through the hooked export `_EffectHandler_t::CreateEffect2(int, RConnector&)` from `_EffectHandler_t::RunFunction`. Children of metas/sequencers are made another way (not seen by the hook). rdb.db is SQLite: `rdb_<type>` tables; names in `rdb_1000010` id 1; meshes `rdb_1010001`; playfield placements `rdb_1000003`.
- `src/features/pfmap`: the playfield map's rooms in alien mission zones ([Effects] AlienMap, on the Misc page; AlienMapTest=1 greens every dungeon map's rooms, for testing outside alien zones; Debug=1 logs each room-tile size once). The dungeon map draws each room's floor textures: `N3!n3GroundRenderer_t::CreateDungeonRoom` sends per tile the first texture of the tilemap's texture table (top bit set = RDB 1010004, general textures; else 1010009, map tiles), MapData_c (GUI 0x10042CC4) loads them, PFMapGroundRenderer_c's room loop (0x10046E28) draws each with 0x10046871 (__thiscall(viewport, RTexture_t*, uv, rect, ARGB), ret 0x14; MODULATE2X). Alien floors are 32x32, dark: black on black. ao-vk's RVK_AlienMap (randy31 DrawPrimitive: triangle list, 32x32 texture -> shader flag 0x200) draws those as solid (0.10, 0.32, 0.14). Clarity redirects the room loop's E8 call (SIG_PFMAP_ROOM_TILE) and gives 32x32 tiles its own 4x4 green texture (game::CreateTextureARGB; not 32x32, so ao-vk's rule doesn't take it). The green is 3/4 of ao-vk's (0xFF143E1B). The game's colour still multiplies in (0x100427A1: 0xFF808080 shown rooms, 0xFFFFFFFF the room you're in = x2). GUI's 32x32 map-marker atlas (view+0x128) isn't drawn through that call.
- `src/features/minimap`: a round minimap ([Minimap], Minimap page: Enabled, Locked, Size, Opacity). A Clarity GUI Window + View whose vtable copy has View::Render replaced; it draws with render_t::RenderTriangleFan (FVF 0x144, XYZRHW|DIFFUSE|TEX1, as the local map), StateBlob_c render states and DeviceState::SetTexture, so it works with any renderer.
  - Map data: MapData_c (SIG_MAPDATA_GET; made at GUI start, not by the map window): +0x08 the AnarchyGround_t outdoors, +0x1C/+0x20 the rooms (0x44 bytes: id, ARGB, position, offset, quaternion, w/h in tiles, floor, tile size, tile DbObject_t*s), +0x2C the current floor, +0x81 / +0x82 show-selected / know-all, +0xC4 the map scale (2 indoors, 4 outdoors). Scale as PFMapRenderer_c: 4 / scale GUI units a metre, x zoom (0.75-1.5, the + / - buttons). Rooms go through pfmap::RoomTileTexture (the alien green). Outdoors: per patch the GetShadowTexture lightmap, a 0xBBFFFFFF wash, then the building map (CreateBuildingMap) and ground texture (CreateHiTexture) multiplied.
  - Markers: N3Msg_GetMapCharacters(500, std::list*, int&) every 100 ms (as MapData_c's +0xD0 timer); categories -> the GUI's 32x32 marker atlas (13 images in 8x8 cells) and 64x64 arrow atlas (16x16 cells), made as the map window makes them (GuiResourceManager images, AllocateTexture + RTexture_t::Load). You: GFX_GUI_MAP_ARROW turned by atan2 of (0,0,1) rotated by N3Msg_GetGlobalCharacterRotation. Category 9 is a cone (turrets: entry +0x24 range in metres, +0x28 half-angle; GUI 0x100EA626 -> 0x10046400, a 0x47FF0000 fan of 8 arc points, after the markers, every floor). Arrows (every floor): the selected target (cell 1) and characters marked by a voice command (cell 2, GFX_GUI_MAP_BIG_ARROW): a voice text starting "[..M..]" (GUI 0x1008C17B) sends GlobalSignals_c +0x150 (Identity, 15 s) into MapData_c's std::map<Identity, __time64_t> (+0xA0, head +0xA4; key +0x10, until +0x18; the game prunes it only while its map window is open, so the minimap checks the time).
  - Planet layer (the layers button): the index file of the player's choice (DValues PlanetMapIndexFile / ShadowlandMapIndexFile, under cd_image/textures/PlanetMap; each level names its own File), PNG tiles decoded with WIC, the planet map window's pixel formula (GUI 0x1004B81A) with N3Msg_GetPositionData; + / - step the levels ([Minimap] PlanetLevel). You: GFX_GUI_PLANETMAP_PLAYER_MARKER, point (8, 8). Playfields not in the coords file (inside): the last place outdoors ([Minimap] LastZone / LastX / LastZ). Dungeons the planet map has a picture of (Saavick's map draws some static dungeons on the map itself, at their own coords entry, e.g. Temple of Three Winds 1931): a playfield on a map where MapData_c has rooms and no ground gets the planet layer whatever [Minimap] Layer says (InMappedDungeon); the layers button there switches for that visit only (g_dungeonLocal, not saved).
  - Frame: a dark gap, the gunmetal ring (r+2..r+9) with teal arcs, a 1 px dark outline; no silver rim. Compass: N/E/S/W badges, the + / - / layers buttons (gunmetal badges, radius 11), and two rim markers: heading (light, pointing in) and the mission waypoint (gold, pointing out; only in your playfield), all centred on the ring (kRingMid); kFramePx 15 leaves room for the badges. The waypoint is GUIModuleActivator_c's (ControlCenterModule_c +0x1A0): +0x08 target Identity, +0x10 position, +0x1C playfield (GUI 0x1002C8F0 sets, 0x1002C918 clears); on the map the local map's GFX_GUI_MAPSQUARE_MISSION, on the planet layer GFX_GUI_PLANETMAP_MISSION_MARKER2 (point (8, 0)). Frame and badges are painted in software (coverage AA) and drawn 1:1 on whole pixels.
  - Input (core/wndproc, 100 ms timer): unlocked, a drag moves the window ([Minimap] X / Y); locked, a drag pans (metres; a click, moving on the local map, or a new playfield centres it again). No mouse wheel.
  - The game's compass (CompassWindow_c "compass_window", GUI 0x1006D433; its CriteriaMonitor_c at +0x74, "dvalue:cc_section1 && dvalue:cc_compass") is hidden while the minimap is enabled (found by RTTI class name in WindowController_c's window list, each tick); when it's turned off, the one Clarity hid is shown again if its condition holds.
  - The game's local map: the GUI module "map_window" (its DValue = open, per character; the toolbar's Map button and the key toggle it). Its handler GUIModuleActivator_c 0x1002D3E3 (SIG_LOCAL_MAP_TOGGLE, __thiscall(GUIModuleBase_c*, bool), ret 8) is hooked: while the minimap is on it makes no window and each call shows / hides the minimap ([Minimap] Shown, the same for every character). The planet map ("planetmap_window") is left alone.
- `src/features/timers`: the game's timer bars, movable ([Bars] TimersLocked, on the Frames page as "Timer Bars Locked", locked by default; TimersX / TimersY). TimerSystemModule_t (GUI exports) keeps the bars in a std::list at +0x28; a bar (TimerBarBase_c, GUI 0x100512AE): +0x04 its RenderWindow_t (128x16, display pixels; the PowerBar_t and the name are drawn in it), +0x18 its slot (0-19, FindNextFreePos). The game places a window once at (40, (slot + 2) * 20) and never moves it. Clarity hooks the private CreateTimer (weak_ptr<TimerEntry_t>, ...; the action bars, GameTimerBar_c) and moves each new bar with RenderWindow_t::Reposition to the stack's place. The public CreateTimer's TimerBar_c is the logout countdown (FlowControlModule_t::CampStartedMessage centres it), left alone. Unlocked, a TimerBar_c of Clarity's own (public CreateTimer, layer 7000, never finishes; DeleteTimer when locked) shows where the stack starts; a left press on a stack bar drags it (client px -> display px with DisplaySystem_t::GetDisplayWidth / Height).
- Nameplate textures are repainted and sent per area (the bar's fill, or the "attacking you" band) with `VisualMaterial_t::Modify(data, pitch, format, RECT*)` (game::ModifyVisualMaterial) instead of the whole 1024x256 texture; a plate's bar at most every 100 ms (kBarEveryMs).
- `src/features/settings`: the Clarity tab in the options window. It registers DValues `CLR_*` with ranges, reads changes with a DistributedValue_c observer, and serves Root.xml by chaining on msvcr100's CreateFileA/W import slots after AOReloaded. The options window only has checkboxes, sliders and radio groups (`OptionRadioButtonGroup`, int variants), no buttons. Pages: Floating Combat Text, Nameplates, Frames (the bars and the timer bars' lock; [Bars] in Clarity.ini), Misc ([Effects]), Minimap ([Minimap]). Only the Floating Combat Text page starts with a Default / Custom radio group (`CLR_Preset*`); Nameplates has Enabled, Style (Classic / Modern), the size and opacity sliders, Overlapping nameplates, the Modern-only options (Item::modern: greyed out through `view_enable_expression="dvalue:CLR_NpModern"`, an unsaved flag Flush keeps up to date, and set back to their defaults when Classic is picked; the options window has no way to hide a control) and a "Nameplates:" group (Players, NPCs and Monsters, Pets), Frames has Enabled, Locked, Size and Timer Bars Locked; Minimap has Enabled, Locked, Size and Opacity. The group heading is an Item's `section` (LARGE only on the Floating Combat Text page): Default sets the page's DValues back with `DistributedValue_c::SetDValue`, and any change by hand switches it to Custom. While Clarity's frames replace the game's bars ([Bars] Enable), the game's own "Show Nano Target" / "Show Fight Target" / "Show Target's Target" options (cc_friendly_health_bar / cc_hostile_health_bar / Targetstarget, drawn in those bars' windows) are greyed out: the Root.xml overlay adds `&& dvalue:CLR_GameTargetBars` to their view_enable_expression, and Flush keeps that unsaved DValue up to date.
